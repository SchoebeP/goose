# Codebase audit — 2026-06-10

Multi-agent audit (14 scoped finders + adversarial verification of every finding) of the
GooseSwift iOS app and the goose-core Rust crate. 81 raw findings; 67 confirmed after
verification, 14 refuted. Severities are post-verification corrected values.

**Status legend:** FIXED — remediated and verified (`cargo test` green, `xcodebuild` succeeds).
Findings whose fix involves on-band behavior include an *On-device validation* checklist —
run it before fully trusting the change. PARTIAL — core fix landed, a documented residual remains.

## swift-ble-core

This scope is the iOS CoreBluetooth client for the WHOOP band: connection lifecycle + background state restoration, dual command framing (GEN4 0xAA/crc8/crc32 for the 4.0 at 61080002, V5 crc16/crc32 for the 5.0 at fd4b0002), the once-per-connection GEN4 enable sequence with 60s re-enable, packet parsing (HR/RR, battery, charging events, historical data), derived vitals (RHR/HRV), and forwarding to the user's own VPS. Overall health is good where it was field-tested: the GEN4 enable cadence, GET_BATTERY uint16/10-at-byte-9 decode, 0x2A19-is-garbage-on-GEN4 rule, offset-20 signed charging current with deadband, and dead-link write-error recovery all match the verified protocol facts, and CoreBluetooth callbacks are consistently re-dispatched to the main thread. The real defects cluster at the edges the band never exercised: a Bluetooth power-cycle permanently strands the auto-reconnect state machine, the "stale link" watchdog only ever sees GEN4 data so it tears down healthy 5.0/standard-HR connections, the V5 historical-sync packet counter is starved by the off-main fast path causing spurious retries/failures, the cloud forwarder keeps reassembly buffers across reconnects and skips CRC-32 checks, an ingest bearer token is committed in source, and two GEN4 watchdog fields are accessed from two threads without synchronization.

### [CRITICAL] VPS ingest bearer token hardcoded and committed in source

- **Where:** `GooseSwift/GooseBLEClient+Parsing.swift:970`
- **Status:** FIXED (2026-06-10)

**Evidence.** `private let token = "c0067852565b4d0d46606172de35c6ba120112c447e1f25b"` with `private let endpoint = URL(string: "https://latenightgames.fr/whoop/ingest/samples")!` — the write credential for the biometric ingest endpoints (/ingest/samples, /ingest/frames, /ingest/logs) on a publicly-reachable host is committed to the git repo (and its history), violating the project's own "never commit secrets" rule. Anyone with repo access can inject forged biometric data or spam the user's VPS; rotating it requires a code change and redeploy.

### [HIGH] Bluetooth power-cycle permanently strands auto-reconnect (activePeripheral never cleared, startup reconnect is once-only)

- **Where:** `GooseSwift/GooseBLEClient+CentralDelegate.swift:74`
- **Status:** FIXED (2026-06-10)

**Evidence.** In centralManagerDidUpdateState: `if central.state == .poweredOn { if !startupReconnectAttempted { startupReconnectAttempted = true; attemptAutomaticReconnect(reason: "startup") } } else { ... updateConnectionState("disconnected") ... connectedAt = nil }`. When Bluetooth powers off, iOS invalidates all peripherals WITHOUT firing didDisconnectPeripheral, but the else-branch never clears `activePeripheral`, `commandCharacteristic`, or `gen4StartedPulseStream`. When Bluetooth comes back on, `startupReconnectAttempted` is already true so nothing runs; `attemptAutomaticReconnect` (GooseBLEClient+Commands.swift:715) bails on `guard activePeripheral == nil else { updateReconnectState("already connected"); return }`, and `healConnectionIfStale` also requires `activePeripheral == nil`. After any BT toggle / bluetoothd reset the app sits disconnected until relaunch — and since steps/PPG are NOT backfillable from the band buffer, that window's accel/optical data is lost.

### [MEDIUM] Stale-link heal tears down healthy connections whose data is not on 6108000x: lastDataFrameAt is only updated for GEN4 characteristics

- **Where:** `GooseSwift/GooseBLEClient+Commands.swift:1112`
- **Status:** FIXED (2026-06-10)

**Evidence.** `healConnectionIfStale`: `if connectionState == "ready", Date().timeIntervalSince(lastDataFrameAt) > 30 { ... recoverFromDeadLink(reason: "stale on \(reason)") }` — but `lastDataFrameAt` is ONLY set in gen4ObserveRawNotification behind `guard uuid.hasPrefix("61080005") || uuid.hasPrefix("61080003") || uuid.hasPrefix("61080004") else { return }` (line 1200-1203). On a WHOOP 5.0 (fd4b000x notifications) or a 4.0 streaming only standard HR on 2A37 (gen4PulseStream defaulted off), lastDataFrameAt stays Date.distantPast forever, so every app foreground (GooseAppModel+Lifecycle.swift:12 calls healConnectionIfStale("foreground")) cancels a perfectly healthy connection via cancelPeripheralConnection — a forced disconnect/reconnect churn that also fails any in-flight historical sync in didDisconnectPeripheral.

**Fix notes / validation.** Implemented the verifier's primary design: (1) fanOutRawNotification (PeripheralDelegate.swift) now sets lastDataFrameAt = Date() for EVERY raw notification — it is the single funnel for all three live paths (2A37 standard-HR fast path, the off-main fd4b/6108 notify fast path, and the main-thread handlePeripheralValueUpdate path), so V5 fd4b000x traffic and standard 2A37 HR now feed the stall watchdog, not just the 6108 family. (2) Removed the now-redundant 6108-gated assignment inside gen4ObserveRawNotification (Commands.swift). (3) Reset lastDataFrameAt = Date() at the single updateConnectionState("ready") site (processDiscoveredCharacteristics) so a fresh connection gets a 30 s heal grace instead of inheriting Date.distantPast or the previous link's stale value, closing the ready-before-first-frame race. The verifier's OPTIONAL belt-and-braces guard (only heal when a stream was started this connection) was deliberately not added: there is no reliable single flag for a manually started V5 capture (startPhysiologySignalCapture sets no persistent state), so the guard could suppress legitimate heals; the two verified churn mechanisms (distantPast init + 6108-only feed) are both removed by the primary fix. The 60 s GEN4 watchdog was left untouched as instructed (already correctly gated). User validation: foreground the app while connected — previously a 5.0/fd4b or 2A37-only link logged 'connection.heal: stale on foreground' plus a forced disconnect/reconnect on every foreground; now that line should appear only after a genuine 30 s of total link silence.

### [MEDIUM] V5 historical sync packet counter starved: type-47/52 frames are excluded from main-thread side effects, causing spurious transfer retries and false sync failures

- **Where:** `GooseSwift/GooseBLEClient+PeripheralDelegate.swift:153`
- **Status:** FIXED (2026-06-10) — validate on device

**Evidence.** `shouldDispatchNotificationSideEffectsToMain` only returns true for `case V5PacketType.commandResponse, .puffinCommandResponse, .event, .metadata, .puffinMetadata` — V5PacketType.historicalData (47) and historicalIMUDataStream (52) fall through to `return false`, so notifications carrying only historical data take the skip path (`recordSkippedNotificationSideEffect ... return`) and never reach handleHistoricalSyncValue. But the sync state machine counts packets exclusively there (GooseBLEClient+HistoricalHandlers.swift:26 `historicalPacketsReceivedThisSync += 1`). With the counter stuck at 0, retryHistoricalTransferAfterIdleIfNeeded (GooseBLEClient+DebugAndSync.swift:391) re-requests the whole transfer up to 3 times (duplicate data pulled from the band) and then `failHistoricalSync("...produced no historical packet bodies...")` — or completes with the misleading "Historical metadata captured but no packet bodies received" — even when every packet actually arrived and was fanned out to the Rust pipeline.

**Fix notes / validation.** Implemented (shares one edit with the duplicate finding below). The code path was unambiguous from source alone, satisfying the needs-device-testing bar: shouldDispatchNotificationSideEffectsToMain whitelisted only packet types 36/38/48/49/56; historicalPacketsReceivedThisSync has exactly one increment site (HistoricalHandlers.swift:26, only reachable via the main-thread handleHistoricalSyncValue); the CBCentralManager delegate always runs on coreBluetoothQueue so the skip always applied. Added 'case V5PacketType.historicalData, V5PacketType.historicalIMUDataStream: if isHistoricalSyncing { return true }; continue' so type-47/52 frames dispatch to main only during an active V5 sync — restoring both the packet counter and the historical_data_idle timer re-arm, while preserving the perf skip for 100 Hz realtime streams outside syncs. GEN4 is provably unaffected: isHistoricalSyncing can only become true via beginHistoricalSync, which hard-guards on supportsV5HistoricalSync (fd4b0002 V5 command characteristic), and the GEN4 backfill path (gen4ObserveRawNotification) runs inside fanOutNotification BEFORE the skip guard. The benign cross-thread read of isHistoricalSyncing is documented in a comment per the verifier's analysis (a stale false at sync start only skips one value; type-36 command responses dispatch regardless). ON-BAND VALIDATION still required (no fd4b strap reachable from code): 1) connect a WHOOP 5.0/fd4b strap and start a historical sync (Connection screen 'Request Historical Packets', or auto-sync on connect); 2) in the app log stream / app_log table, confirm 'historical_sync.packet' lines with increasing count > 0 during the transfer; 3) confirm NO 'historical_sync.transfer.retry' lines while data is streaming, and that the completion toast reports 'N historical packets captured' instead of 'Historical metadata captured but no packet bodies received'; 4) regression-check the 4.0 band: gen4.history.request still produces type-47 acks and VPS hr_sample backfill rows (path untouched).

### [MEDIUM] WhoopCloudForwarder frame reassembly buffers survive disconnects and frames are forwarded/decoded without CRC-32 verification

- **Where:** `GooseSwift/GooseBLEClient+Parsing.swift:1018`
- **Status:** FIXED (2026-06-10)

**Evidence.** `ingestRawFrame`: `var buf = self.frameBuffers[uuid] ?? []; buf.append(contentsOf: bytes); ... if end > buf.count { break } ... self.frameBuffers[uuid] = buf` — frameBuffers are never cleared on disconnect/reconnect (no reset API exists and didDisconnectPeripheral never calls one). A connection dropped mid-frame leaves a stale 0xAA header whose declared length then swallows the next connection's bytes, emitting chimera frames to the VPS and misaligning the parser until a lucky resync. Compounding it, neither this reassembler nor gen4ObserveRawNotification (which decodes battery at bytes[9..10] and charging at bytes[20..21] on-device) validates the trailing CRC-32 that the protocol mandates ('last 4 bytes are a CRC-32 over the preceding 92'), so misframed/corrupt frames are accepted as truth.

**Fix notes / validation.** CRC validation implemented in ingestRawFrame: header crc8Gen4 over the two length bytes checked against frame[3], and the trailing CRC-32 verified before a frame is appended to pendingFrames (on mismatch the scanner advances 1 byte to resync instead of i=end, which drops chimera frames and self-heals misalignment). Added func resetFrameReassembly() to WhoopCloudForwarder (queue.async { frameBuffers.removeAll() }; pendingFrames/outbox untouched per the verifier's guidance). PARTIAL because the two call sites are in files outside my allowed list — wiring needed: (1) GooseSwift/GooseBLEClient+CentralDelegate.swift, inside centralManager(_:didDisconnectPeripheral:error:) right after 'gen4ReEnableTimer = nil' (line ~275): add 'WhoopCloudForwarder.shared.resetFrameReassembly()'; (2) GooseSwift/GooseBLEClient+Commands.swift, inside recoverFromDeadLink(reason:) after 'gen4ReEnableTimer = nil' (line ~702): same one-liner (belt-and-braces — cancelPeripheralConnection normally triggers the didDisconnect path); optionally also in didConnect. Note: even unwired, the CRC validation alone neutralizes the chimera-upload bug — a stale partial frame fused with the next connection's bytes now fails CRC-32 and is skipped byte-by-byte until the next genuine header (proven by simulation against real captured frames). The verifier's optional lower-priority suggestion of CRC checks before the on-device battery/charging decodes at Commands.swift:1214/1261 was not implemented (file not in allowed list; verifier rated it low priority since those read raw single notifications unaffected by reassembly state).

### [LOW] Data race on gen4 watchdog state: lastDataFrameAt written on the CoreBluetooth queue, read on main; gen4HistoryDeadline written on main, read under a lock only on the reader side

- **Where:** `GooseSwift/GooseBLEClient+Commands.swift:1203`
- **Status:** FIXED (2026-06-10)

**Evidence.** `lastDataFrameAt = Date()   // stall watchdog: any notification = data is flowing` executes inside gen4ObserveRawNotification, which the fast path in peripheral(_:didUpdateValueFor:) invokes directly on coreBluetoothQueue (via fanOutRawNotification at GooseBLEClient+PeripheralDelegate.swift:79/93/216), while the 60s gen4ReEnableTimer (line 1095) and healConnectionIfStale (line 1112) read it on the main thread with no synchronization. Similarly `gen4HistoryDeadline` is written on main (line 1168, CentralDelegate.swift:242, Commands.swift:700) but read inside gen4ProbeLock on the CB queue (line 1233) — locking only the reader does not synchronize with unlocked writers. Unsynchronized cross-thread access to non-atomic vars is undefined behavior in Swift; despite the function's 'Thread-safe' doc comment, these two fields are not.

**Fix notes / validation.** Fixed with a deliberate deviation from the letter of the refined_fix, for a constraint the verifier did not have: one gen4HistoryDeadline writer lives in GooseBLEClient+CentralDelegate.swift (two sites: bluetooth power-off teardown and didDisconnectPeripheral), which is NOT in my allowed-edit set. Instead of locking each call site, both fields are now lock-guarded computed properties in GooseBLEClient.swift over `private` backing fields (_lastDataFrameAt, _gen4HistoryDeadline), with get/set taking the existing gen4ProbeLock — this synchronizes every current and future reader/writer in ALL files (including the unallowed CentralDelegate sites, which now route through the locked setter unmodified) and matches the verifier's own 'private(set) behind the accessors' suggestion. The `private` access level prevents any other file from bypassing the lock. Deadlock audit: the only code that touched these fields while already holding gen4ProbeLock was the type-47 ACK block in gen4ObserveRawNotification — restructured so gen4HistoryDeadline is read via the (self-locking) accessor BEFORE gen4ProbeLock is taken (NSLock is non-recursive); the gen4LastHistoryAck throttle stays under the lock. The frame-counter lock block touches neither field. The new fanOutRawNotification write and the ready-reset write from finding 1 are automatically covered by the locked setter.

## swift-ble-historical

This scope is the iOS app's V5 historical backfill subsystem: GooseBLEClient+HistoricalCommands.swift builds and writes the GET_DATA_RANGE(34)/SEND_HISTORICAL_DATA(22)/HISTORICAL_DATA_RESULT(23) command frames (command numbers match the field-verified protocol), GooseBLEClient+HistoricalHandlers.swift runs the response/metadata state machine (HistoryStart/End/Complete, ACK queueing, idle/retry/fail paths), and HistoryCandidateSamples.swift is read-only diagnostic decoding of candidate temperature/respiration/motion fields (clean: callers pass fresh zero-based Data, bounds are guarded, values are explicitly labelled unverified candidates). The state machine itself is unusually well-hardened — run-ID-guarded DispatchWorkItems, sequence-matched responses, PENDING grace handling, capped retries, dead-link write recovery — but its packet accounting is starved by a notification fast-path one file over: data-only type-47/52 values never reach handleHistoricalSyncValue, so the packet counter and data-idle re-arm are dead, which in turn corrupts the retry/complete decisions and defeats the ack-disabled "preserve queue" suppression (band-side trim of data the user asked to keep). The remaining issues are a fire-and-forget final ACK whose write failure is invisible after early completion, and an off-by-one in the ACK payload builder. No privacy violations found in this scope: all writes go to the band; logging/telemetry goes through the app's own record/onHistoricalRangeTelemetry hooks.

### [HIGH] "Preserve unread queue" mode still sends the HISTORICAL_DATA_RESULT trim ACK whenever the packet counter is 0 — which, given the counter bug, is effectively always — so the band's buffer is trimmed in the one mode that promises not to consume it

- **Where:** `GooseSwift/GooseBLEClient+DebugAndSync.swift:340`
- **Status:** FIXED (2026-06-10)

**Evidence.** `if !historicalDataResultAckEnabled && historicalPacketsReceivedThisSync > 0 { ... suppressed ... return true }` followed by `if !historicalDataResultAckEnabled { record(... "historical_sync.result_ack.metadata_only" ...) } ; historyEndAckSentThisBurst = true; writeHistoricalCommand(.historicalDataResult)` (DebugAndSync.swift:340-364). Suppression of the trim ACK in ack-disabled mode (`syncHistoricalPacketsPreservingUnreadQueue`, UserActions.swift:238-246, logged as "ack=disabled") is conditioned on `historicalPacketsReceivedThisSync > 0`. Because data frames bypass the handler (see counter finding), the count is ~always 0, so the code falls through and sends the HISTORICAL_DATA_RESULT built from the HistoryEnd trim payload anyway — advancing the band's onboard trim pointer for data the user explicitly asked to leave queued. The band's ~days buffer is the only copy of un-pulled history in this local-first design, so an unwanted trim is unrecoverable on the band side. Even with the counter fixed, gating a 'never consume' debug mode on a local packet count is wrong: a burst whose data frames were dropped/uncounted still gets its queue trimmed.

**Fix notes / validation.** Implemented part (a) of the refined fix exactly: in processQueuedHistoricalDataResultAck the two ack-disabled branches are merged into one — when historicalDataResultAckEnabled is false the code now unconditionally records 'historical_sync.result_ack.suppressed' (with packets= count), then calls retryHistoricalTransferAfterIdleIfNeeded (which internally guards on historicalPacketsReceivedThisSync == 0, so the explicit count check in the refined fix is subsumed) and otherwise completeHistoricalSync(reason: "history_result_ack_suppressed_<reason>"). writeHistoricalCommand(.historicalDataResult) is now unreachable in ack-disabled mode from every funnel point (history_end metadata, history_complete re-queue, after-command-response, idle work item), so preserve mode can never trim the band's onboard queue. The dead 'historical_sync.result_ack.metadata_only' branch was removed (no other references to that log title exist). Part (b) — the packet-counter undercount fix (adding historicalData/historicalIMUDataStream to shouldDispatchNotificationSideEffectsToMain or counting on the CB queue) — lives in GooseBLEClient+PeripheralDelegate.swift / GooseBLEClient+HistoricalHandlers.swift, which are OUTSIDE my allowed file list (the spec evidence calls it a separate 'counter finding', presumably owned by another agent). Consequence until (b) lands: a preserve-mode sync whose data frames bypass the main handler reports count==0 and now ends in retry (max 3 GET_DATA_RANGE/SEND_HISTORICAL_DATA attempts) then 'Sync Failed' instead of silently trimming the queue — the safe failure direction: no band-side data loss, and the burst data still reaches the phone via the raw fan-out/spool on each attempt. If the counter finding is NOT being fixed by another agent, it still needs to land for preserve-mode syncs to report 'synced'.

### [MEDIUM] Historical data packets (type-47/52) never reach the sync handler: packet counter stays 0 and the data-idle re-arm is dead, so successful backfills are retried and then reported as failed

- **Where:** `GooseSwift/GooseBLEClient+PeripheralDelegate.swift:152`
- **Status:** FIXED (2026-06-10) — validate on device

**Evidence.** The off-main fast path in didUpdateValueFor (lines 83-98) skips main-thread side effects for any notification value that contains no control frame: `guard shouldDispatchNotificationSideEffectsToMain(value, characteristic: characteristic) else { recordSkippedNotificationSideEffect(...); return }`. That predicate whitelists only `case V5PacketType.commandResponse, V5PacketType.puffinCommandResponse, V5PacketType.event, V5PacketType.metadata, V5PacketType.puffinMetadata: return true` — it omits `V5PacketType.historicalData` (47) and `historicalIMUDataStream` (52). The CBCentralManager is created on `coreBluetoothQueue` (GooseBLEClient+Commands.swift:10-16), so the delegate is always off-main and this fast path always applies. Consequently `handleHistoricalSyncValue` (GooseBLEClient+HistoricalHandlers.swift:7) is never invoked for data-only values, and the in-scope accounting `case V5PacketType.historicalData, V5PacketType.historicalIMUDataStream: historicalPacketsReceivedThisSync += 1 ... scheduleHistoricalIdleCompletion(reason: "historical_data_idle")` (HistoricalHandlers.swift:25-28) is dead for the bulk of the transfer (type-47 bursts are almost entirely data frames; only values that happen to also carry a metadata/response frame get through). Effects: (1) any chunk that streams >12s of pure data between metadata frames lets `historicalIdleWorkItem` fire mid-transfer; `retryHistoricalTransferAfterIdleIfNeeded` (DebugAndSync.swift:389-393) guards on `historicalPacketsReceivedThisSync == 0`, sees 0, and re-issues GET_DATA_RANGE into a live stream, and after `historicalTransferMaxRequestAttempts = 3` calls `failHistoricalSync("...produced no historical packet bodies...")` even though packets flowed the whole time; (2) after HistoryComplete the same count==0 path triggers spurious full re-pull cycles instead of `completeHistoricalSync`; (3) progress callbacks and the completion toast always report 0 packets ("No missed packets found" / "Historical metadata captured but no packet bodies received"); (4) it breaks the preserve-mode ACK suppression (see separate finding). historicalPacketsReceivedThisSync has exactly one increment site (HistoricalHandlers.swift:26) — there is no alternate counting path.

**Fix notes / validation.** Same root cause as the finding above — fixed by the single shouldDispatchNotificationSideEffectsToMain edit (historicalData/historicalIMUDataStream dispatch to main while isHistoricalSyncing). This restores the counter increment, the idle-timer re-arm at HistoricalHandlers.swift:25-28 (so the 12 s idle no longer fires mid-transfer and retryHistoricalTransferAfterIdleIfNeeded no longer re-requests/falsely fails a healthy transfer), correct progress/toast packet counts, and the count-dependent ACK suppression. See the previous entry for the exact on-band validation steps on a V5/fd4b strap.

### [LOW] Sync can be declared "synced" the moment the final HISTORICAL_DATA_RESULT write is queued; a subsequent write failure (e.g. dead link) is silently ignored because isHistoricalSyncing is already false

- **Where:** `GooseSwift/GooseBLEClient+HistoricalCommands.swift:133`
- **Status:** FIXED (2026-06-10)

**Evidence.** In writeHistoricalCommand, the ACK is fire-and-forget: `pendingHistoricalCommand = nil; historicalCommandTimeoutWorkItem?.cancel()` (lines 100-101), then right after `activePeripheral.writeValue(...)` it runs `if historyCompleteReceived { completeHistoricalSync(reason: "history_result_ack_sent_after_complete") }` (lines 133-137), setting isHistoricalSyncing=false before CoreBluetooth confirms the write. The write-error path in didWriteValueFor only fails the sync `if isHistoricalSyncing && characteristic.uuid == commandCharacteristic?.uuid` (PeripheralDelegate.swift:307-309), so a failed final ACK write (including the documented zombie-link "The specified device is not connected." case) leaves the UI showing "Synced" while the band never received the trim ACK. Side effect: the unreachable `.historicalDataResult` response branch in handleHistoricalCommandResponse (HistoricalHandlers.swift:482-489) can never match because pendingHistoricalCommand was cleared, so a band-side FAILURE result for the ACK is also invisible. Consequence is bounded — the band re-sends the untrimmed chunk on the next sync (duplicates downstream) rather than losing data — but the success report is wrong and the duplicate re-pull is unexplained to the user.

**Fix notes / validation.** Implemented with a deliberate design-around of the refined fix: the refined version wanted a stored awaiting-confirmation flag plus a hook in peripheral(_:didWriteValueFor:) success branch, but the flag needs a stored property on GooseBLEClient.swift (owned by another agent; extensions can't add stored state) and the delegate lives in GooseBLEClient+PeripheralDelegate.swift (not in my allowed list). Equivalent behavior achieved entirely within allowed files: in writeHistoricalCommand (HistoricalCommands.swift:133-141), when kind == .historicalDataResult and historyCompleteReceived, the .withoutResponse case still completes immediately (didWriteValueFor never fires for those, exactly as the refined fix specifies), but the .withResponse case now calls new scheduleHistoricalResultAckWriteGrace() (DebugAndSync.swift:381-400) instead of completing synchronously. That helper keeps isHistoricalSyncing == true for a 5 s grace window (run-ID-guarded DispatchQueue.main.asyncAfter closure — no stored property needed; stale fires no-op via historicalSyncRunID/isHistoricalSyncing guards) and cancels historicalIdleWorkItem/historicalRangeRetryWorkItem/readySyncWorkItem up front, preserving the exact cancellation semantics the old synchronous completeHistoricalSync had at this point so nothing else can fire during the window. Net effect: a failed final ACK write (including the documented zombie-link 'specified device is not connected' error, which CoreBluetooth returns near-instantly) now hits the existing PeripheralDelegate error branch (isHistoricalSyncing && commandCharacteristic) and fails the sync with the real error instead of showing a false 'Synced'; on success the sync completes at the 5 s fallback with reason 'history_result_ack_write_grace_elapsed'. Known trade-off vs the refined fix: without the didWriteValueFor success hook, the happy path always waits the full 5 s grace (the refined fix's own fallback), so the 'Synced' toast/terminal progress callback arrives ~5 s later — verified the only terminal-progress consumer (overnight final-sync drain in GooseAppModel+OvernightRun.swift) has no timeout, so this is safe; and a genuine ATT-level write timeout (~30 s) still escapes the window, same as the refined fix's fallback accepted. The sync can never hang: the closure always either no-ops or completes. The dead .historicalDataResult response branch in handleHistoricalCommandResponse noted in the evidence is in HistoricalHandlers.swift (not allowed) and was a side observation, not part of the fix.

## swift-appmodel

This scope is the iOS app's central coordination layer: GooseAppModel (a @MainActor ObservableObject) plus extensions that route raw BLE notifications through reassembly/parse/import queues, run timed health-packet capture sessions, drive the Overnight Guard state machine (JSONL spool + SQLite mirror + manifest/status sidecars + final historical sync + export), record activities, and coalesce UI state via aggregators. Overall the code is unusually defensive — bounded write queues, throttled publishing, queue-confined reassembly buffers, lock-protected depth counters — and contains no third-party endpoints (privacy constraint holds). The real weaknesses are at the edges: the overnight final-sync state machine can wedge with no retry or timeout, per-packet synchronous status-file rewrites on the main thread during sync bursts, MainActor state read unsynchronized from the CoreBluetooth queue (masked by Swift 5.0 language mode), synchronous spool I/O on the CoreBluetooth queue during guard sessions, an error path that leaves a capture session permanently open, and a background-task expiration handler that ends its task asynchronously.

### [MEDIUM] Overnight final sync wedges permanently if historical sync is blocked after the live-stream pause (no retry, no timeout, polls disabled, background task leaked)

- **Where:** `GooseSwift/GooseAppModel+OvernightRun.swift:140`
- **Status:** FIXED (2026-06-10)

**Evidence.** In requestOvernightGuardFinalSync, after setting overnightGuardFinalSyncPending = true, cancelling range polls, beginning a critical background task, and stopping the live physiology streams, the 2.2 s continuation bails out without any cleanup: `guard self.ble.canSyncHistorical else { self.overnightGuardStatus = "Final sync blocked after live-stream pause: \(self.ble.historicalSyncStatus)" ... return }`. overnightGuardFinalSyncPending stays true forever: re-tapping final sync hits `guard !overnightGuardFinalSyncPending else { overnightGuardStatus = "Final sync already running"; return }` (line 109), scheduleOvernightGuardRangePoll refuses to run (`guard overnightGuardActive, !overnightGuardFinalSyncPending`, line 378), live capture has already been stopped, and the critical background task begun at line 122 is never ended (it leaks until iOS force-expires it). The same wedge occurs if the sync starts but never reaches a terminal GooseHistoricalSyncProgress (e.g. the documented silent-disconnect dead-link) — there is no watchdog/timeout covering the finalSyncPending state.
