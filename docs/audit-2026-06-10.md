# Codebase audit — 2026-06-10

Multi-agent audit (14 scoped finders + adversarial verification of every finding) of the
GooseSwift iOS app and the goose-core Rust crate. 81 raw findings; 67 confirmed after
verification, 14 refuted. Severities below are the post-verification corrected values.

Findings marked **FIXED (2026-06-10)** were remediated in the commits accompanying this report.
Open findings include the verifier's refined fix, ready to apply.

## swift-ble-core

This scope is the iOS CoreBluetooth client for the WHOOP band: connection lifecycle + background state restoration, dual command framing (GEN4 0xAA/crc8/crc32 for the 4.0 at 61080002, V5 crc16/crc32 for the 5.0 at fd4b0002), the once-per-connection GEN4 enable sequence with 60s re-enable, packet parsing (HR/RR, battery, charging events, historical data), derived vitals (RHR/HRV), and forwarding to the user's own VPS. Overall health is good where it was field-tested: the GEN4 enable cadence, GET_BATTERY uint16/10-at-byte-9 decode, 0x2A19-is-garbage-on-GEN4 rule, offset-20 signed charging current with deadband, and dead-link write-error recovery all match the verified protocol facts, and CoreBluetooth callbacks are consistently re-dispatched to the main thread. The real defects cluster at the edges the band never exercised: a Bluetooth power-cycle permanently strands the auto-reconnect state machine, the "stale link" watchdog only ever sees GEN4 data so it tears down healthy 5.0/standard-HR connections, the V5 historical-sync packet counter is starved by the off-main fast path causing spurious retries/failures, the cloud forwarder keeps reassembly buffers across reconnects and skips CRC-32 checks, an ingest bearer token is committed in source, and two GEN4 watchdog fields are accessed from two threads without synchronization.

### [CRITICAL] VPS ingest bearer token hardcoded and committed in source

- **Where:** `GooseSwift/GooseBLEClient+Parsing.swift:970`
- **Status:** FIXED (2026-06-10)  |  verifier confidence: high  |  fix risk: safe

**Evidence.** `private let token = "c0067852565b4d0d46606172de35c6ba120112c447e1f25b"` with `private let endpoint = URL(string: "https://latenightgames.fr/whoop/ingest/samples")!` — the write credential for the biometric ingest endpoints (/ingest/samples, /ingest/frames, /ingest/logs) on a publicly-reachable host is committed to the git repo (and its history), violating the project's own "never commit secrets" rule. Anyone with repo access can inject forged biometric data or spam the user's VPS; rotating it requires a code change and redeploy.

### [HIGH] Bluetooth power-cycle permanently strands auto-reconnect (activePeripheral never cleared, startup reconnect is once-only)

- **Where:** `GooseSwift/GooseBLEClient+CentralDelegate.swift:74`
- **Status:** FIXED (2026-06-10)  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** In centralManagerDidUpdateState: `if central.state == .poweredOn { if !startupReconnectAttempted { startupReconnectAttempted = true; attemptAutomaticReconnect(reason: "startup") } } else { ... updateConnectionState("disconnected") ... connectedAt = nil }`. When Bluetooth powers off, iOS invalidates all peripherals WITHOUT firing didDisconnectPeripheral, but the else-branch never clears `activePeripheral`, `commandCharacteristic`, or `gen4StartedPulseStream`. When Bluetooth comes back on, `startupReconnectAttempted` is already true so nothing runs; `attemptAutomaticReconnect` (GooseBLEClient+Commands.swift:715) bails on `guard activePeripheral == nil else { updateReconnectState("already connected"); return }`, and `healConnectionIfStale` also requires `activePeripheral == nil`. After any BT toggle / bluetoothd reset the app sits disconnected until relaunch — and since steps/PPG are NOT backfillable from the band buffer, that window's accel/optical data is lost.

### [MEDIUM] Stale-link heal tears down healthy connections whose data is not on 6108000x: lastDataFrameAt is only updated for GEN4 characteristics

- **Where:** `GooseSwift/GooseBLEClient+Commands.swift:1112`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** `healConnectionIfStale`: `if connectionState == "ready", Date().timeIntervalSince(lastDataFrameAt) > 30 { ... recoverFromDeadLink(reason: "stale on \(reason)") }` — but `lastDataFrameAt` is ONLY set in gen4ObserveRawNotification behind `guard uuid.hasPrefix("61080005") || uuid.hasPrefix("61080003") || uuid.hasPrefix("61080004") else { return }` (line 1200-1203). On a WHOOP 5.0 (fd4b000x notifications) or a 4.0 streaming only standard HR on 2A37 (gen4PulseStream defaulted off), lastDataFrameAt stays Date.distantPast forever, so every app foreground (GooseAppModel+Lifecycle.swift:12 calls healConnectionIfStale("foreground")) cancels a perfectly healthy connection via cancelPeripheralConnection — a forced disconnect/reconnect churn that also fails any in-flight historical sync in didDisconnectPeripheral.

**Refined fix.** In GooseBLEClient+PeripheralDelegate.swift fanOutRawNotification (line 215), set `lastDataFrameAt = Date()` for every data-bearing notification before calling gen4ObserveRawNotification (and remove the now-redundant assignment at Commands.swift:1203). This covers fd4b0003/4/5/7 and 2A37 as well as the 6108 family, with no new threading concern — gen4ObserveRawNotification already performs this same off-main assignment today. Additionally, reset `lastDataFrameAt = Date()` when the connection becomes ready (Commands.swift:926, next to updateConnectionState("ready")) so a fresh connection gets a 30s grace period instead of inheriting distantPast or a pre-disconnect stale value, closing the ready-before-first-frame race. Optionally, as a belt-and-braces guard, make the stale branch of healConnectionIfStale require that some data stream was actually started this connection (e.g. gen4StartedPulseStream || a V5 capture active) before forcing recoverFromDeadLink. Do NOT touch the 60s watchdog — it is already correctly gated to the GEN4 path.

### [MEDIUM] V5 historical sync packet counter starved: type-47/52 frames are excluded from main-thread side effects, causing spurious transfer retries and false sync failures

- **Where:** `GooseSwift/GooseBLEClient+PeripheralDelegate.swift:153`
- **Status:** open  |  verifier confidence: medium  |  fix risk: needs-device-testing

**Evidence.** `shouldDispatchNotificationSideEffectsToMain` only returns true for `case V5PacketType.commandResponse, .puffinCommandResponse, .event, .metadata, .puffinMetadata` — V5PacketType.historicalData (47) and historicalIMUDataStream (52) fall through to `return false`, so notifications carrying only historical data take the skip path (`recordSkippedNotificationSideEffect ... return`) and never reach handleHistoricalSyncValue. But the sync state machine counts packets exclusively there (GooseBLEClient+HistoricalHandlers.swift:26 `historicalPacketsReceivedThisSync += 1`). With the counter stuck at 0, retryHistoricalTransferAfterIdleIfNeeded (GooseBLEClient+DebugAndSync.swift:391) re-requests the whole transfer up to 3 times (duplicate data pulled from the band) and then `failHistoricalSync("...produced no historical packet bodies...")` — or completes with the misleading "Historical metadata captured but no packet bodies received" — even when every packet actually arrived and was fanned out to the Rust pipeline.

**Refined fix.** In shouldDispatchNotificationSideEffectsToMain (GooseSwift/GooseBLEClient+PeripheralDelegate.swift:152-161), add a case so historical frames dispatch to main only while a sync is active: `case V5PacketType.historicalData, V5PacketType.historicalIMUDataStream: if isHistoricalSyncing { return true }; continue`. This preserves the perf skip for ordinary sensor streams (type-43 etc.) outside syncs, and restores BOTH the packet counter (HistoricalHandlers.swift:26) and the idle-timer refresh (scheduleHistoricalIdleCompletion("historical_data_idle"), HistoricalHandlers.swift:28) — a counter-only atomic fix would still let the 12s idle timer fire mid-transfer. Note isHistoricalSyncing is main-thread state read from coreBluetoothQueue; the race is benign (a stale false just skips one value at sync start — acceptable since the first GET_DATA_RANGE/SEND_HISTORICAL_DATA command responses are type-36 and dispatch anyway, and sync teardown only flips it back on main). Historical bursts are bounded, so main-thread load is acceptable; if profiling disagrees, fall back to a lock-protected fast-path counter plus throttled main-queue publish that also reschedules the idle work item. Must be validated on a real WHOOP 5.0/fd4b band (confirm historical_sync.packet counts > 0 and no transfer retries in app_log); the GEN4/WHOOP 4.0 backfill path (gen4ObserveRawNotification) is unaffected and needs no change.

### [MEDIUM] WhoopCloudForwarder frame reassembly buffers survive disconnects and frames are forwarded/decoded without CRC-32 verification

- **Where:** `GooseSwift/GooseBLEClient+Parsing.swift:1018`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** `ingestRawFrame`: `var buf = self.frameBuffers[uuid] ?? []; buf.append(contentsOf: bytes); ... if end > buf.count { break } ... self.frameBuffers[uuid] = buf` — frameBuffers are never cleared on disconnect/reconnect (no reset API exists and didDisconnectPeripheral never calls one). A connection dropped mid-frame leaves a stale 0xAA header whose declared length then swallows the next connection's bytes, emitting chimera frames to the VPS and misaligning the parser until a lucky resync. Compounding it, neither this reassembler nor gen4ObserveRawNotification (which decodes battery at bytes[9..10] and charging at bytes[20..21] on-device) validates the trailing CRC-32 that the protocol mandates ('last 4 bytes are a CRC-32 over the preceding 92'), so misframed/corrupt frames are accepted as truth.

**Refined fix.** In GooseBLEClient+Parsing.swift add to WhoopCloudForwarder: `func resetFrameReassembly() { queue.async { self.frameBuffers.removeAll() } }` (leave pendingFrames/outbox alone — those hold complete frames). Call WhoopCloudForwarder.shared.resetFrameReassembly() from didDisconnectPeripheral in GooseBLEClient+CentralDelegate.swift (around line 240, beside the gen4StartedPulseStream re-arm) and from recoverFromDeadLink in GooseBLEClient+Commands.swift (around line 700); optionally also on didConnect for belt-and-braces. Separately, before appending a reassembled frame to pendingFrames (Parsing.swift line 1028-1031), verify the trailing 4 bytes equal Gen4Frame.crc32 over the frame body per the GEN4 layout; on mismatch advance i by 1 (treat the 0xAA as a false header) instead of i = end, which both drops chimera frames and self-heals the misalignment immediately. Adding the same CRC check (or at least the header crc8) before the on-device battery decode at Commands.swift:1214 and charging-current decode at line 1261 is a cheap robustness win but lower priority since those read raw single notifications.

### [LOW] Data race on gen4 watchdog state: lastDataFrameAt written on the CoreBluetooth queue, read on main; gen4HistoryDeadline written on main, read under a lock only on the reader side

- **Where:** `GooseSwift/GooseBLEClient+Commands.swift:1203`
- **Status:** open  |  verifier confidence: high  |  fix risk: safe

**Evidence.** `lastDataFrameAt = Date()   // stall watchdog: any notification = data is flowing` executes inside gen4ObserveRawNotification, which the fast path in peripheral(_:didUpdateValueFor:) invokes directly on coreBluetoothQueue (via fanOutRawNotification at GooseBLEClient+PeripheralDelegate.swift:79/93/216), while the 60s gen4ReEnableTimer (line 1095) and healConnectionIfStale (line 1112) read it on the main thread with no synchronization. Similarly `gen4HistoryDeadline` is written on main (line 1168, CentralDelegate.swift:242, Commands.swift:700) but read inside gen4ProbeLock on the CB queue (line 1233) — locking only the reader does not synchronize with unlocked writers. Unsynchronized cross-thread access to non-atomic vars is undefined behavior in Swift; despite the function's 'Thread-safe' doc comment, these two fields are not.

**Refined fix.** Use the existing `gen4ProbeLock` on both sides for both fields (it is uncontended and already taken in the same hot function, so cost is nil). Concretely: (a) in `gen4ObserveRawNotification` (GooseBLEClient+Commands.swift:1203) replace the bare write with `gen4ProbeLock.lock(); lastDataFrameAt = Date(); gen4ProbeLock.unlock()` — note it must stay before the `value.count >= 7` early return so every notification still feeds the watchdog; (b) add a small locked accessor on GooseBLEClient, e.g. `var lastDataFrameAtSynced: Date { gen4ProbeLock.lock(); defer { gen4ProbeLock.unlock() }; return lastDataFrameAt }`, and use it in the timer closure (Commands.swift:1095) and `healConnectionIfStale` (Commands.swift:1112); (c) wrap the three `gen4HistoryDeadline` writes (Commands.swift:700, Commands.swift:1168, GooseBLEClient+CentralDelegate.swift:242) in the same lock — the reader at Commands.swift:1233 already holds it. Optionally make the fields `private(set)` behind the accessors to prevent future unlocked access. Equivalent alternative: an `OSAllocatedUnfairLock<(lastDataFrameAt: Date, gen4HistoryDeadline: Date?, gen4LastHistoryAck: Date)>` bundling the watchdog state, but the NSLock extension is the minimal safe change.

## swift-ble-historical

This scope is the iOS app's V5 historical backfill subsystem: GooseBLEClient+HistoricalCommands.swift builds and writes the GET_DATA_RANGE(34)/SEND_HISTORICAL_DATA(22)/HISTORICAL_DATA_RESULT(23) command frames (command numbers match the field-verified protocol), GooseBLEClient+HistoricalHandlers.swift runs the response/metadata state machine (HistoryStart/End/Complete, ACK queueing, idle/retry/fail paths), and HistoryCandidateSamples.swift is read-only diagnostic decoding of candidate temperature/respiration/motion fields (clean: callers pass fresh zero-based Data, bounds are guarded, values are explicitly labelled unverified candidates). The state machine itself is unusually well-hardened — run-ID-guarded DispatchWorkItems, sequence-matched responses, PENDING grace handling, capped retries, dead-link write recovery — but its packet accounting is starved by a notification fast-path one file over: data-only type-47/52 values never reach handleHistoricalSyncValue, so the packet counter and data-idle re-arm are dead, which in turn corrupts the retry/complete decisions and defeats the ack-disabled "preserve queue" suppression (band-side trim of data the user asked to keep). The remaining issues are a fire-and-forget final ACK whose write failure is invisible after early completion, and an off-by-one in the ACK payload builder. No privacy violations found in this scope: all writes go to the band; logging/telemetry goes through the app's own record/onHistoricalRangeTelemetry hooks.

### [HIGH] "Preserve unread queue" mode still sends the HISTORICAL_DATA_RESULT trim ACK whenever the packet counter is 0 — which, given the counter bug, is effectively always — so the band's buffer is trimmed in the one mode that promises not to consume it

- **Where:** `GooseSwift/GooseBLEClient+DebugAndSync.swift:340`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** `if !historicalDataResultAckEnabled && historicalPacketsReceivedThisSync > 0 { ... suppressed ... return true }` followed by `if !historicalDataResultAckEnabled { record(... "historical_sync.result_ack.metadata_only" ...) } ; historyEndAckSentThisBurst = true; writeHistoricalCommand(.historicalDataResult)` (DebugAndSync.swift:340-364). Suppression of the trim ACK in ack-disabled mode (`syncHistoricalPacketsPreservingUnreadQueue`, UserActions.swift:238-246, logged as "ack=disabled") is conditioned on `historicalPacketsReceivedThisSync > 0`. Because data frames bypass the handler (see counter finding), the count is ~always 0, so the code falls through and sends the HISTORICAL_DATA_RESULT built from the HistoryEnd trim payload anyway — advancing the band's onboard trim pointer for data the user explicitly asked to leave queued. The band's ~days buffer is the only copy of un-pulled history in this local-first design, so an unwanted trim is unrecoverable on the band side. Even with the counter fixed, gating a 'never consume' debug mode on a local packet count is wrong: a burst whose data frames were dropped/uncounted still gets its queue trimmed.

**Refined fix.** Two coordinated changes. (a) In processQueuedHistoricalDataResultAck (GooseBLEClient+DebugAndSync.swift:340-364): make writeHistoricalCommand(.historicalDataResult) unreachable whenever historicalDataResultAckEnabled is false — merge the two ack-disabled branches into one: record 'historical_sync.result_ack.suppressed' (include packets= count), then if historicalPacketsReceivedThisSync == 0 && retryHistoricalTransferAfterIdleIfNeeded(...) return true, else completeHistoricalSync(reason: "history_result_ack_suppressed_\(reason)"); return true. (b) Fix the undercount so preserve-mode runs don't degenerate into retry-then-fail: either add V5PacketType.historicalData and V5PacketType.historicalIMUDataStream to the allow-list in shouldDispatchNotificationSideEffectsToMain (PeripheralDelegate.swift:152-161) — simplest, but re-dispatches every burst value to main, partially defeating the perf optimization — or keep the fast path and increment a counter on the CB queue before the skip (e.g., count type-47/52 frames in the skipped value and add them to historicalPacketsReceivedThisSync via a thread-safe/main-hopped increment, alongside recordSkippedNotificationSideEffect). Note fix (a) alone is safe against trimming but, with the counter still broken, metadata-plus-data bursts report count==0 and trigger retryHistoricalTransferAfterIdleIfNeeded up to historicalTransferMaxRequestAttempts then failHistoricalSync — so ship (a) and (b) together. The historyComplete re-queue path (HistoricalHandlers.swift:586-589) funnels through the same function, so it is covered by (a).

### [MEDIUM] Historical data packets (type-47/52) never reach the sync handler: packet counter stays 0 and the data-idle re-arm is dead, so successful backfills are retried and then reported as failed

- **Where:** `GooseSwift/GooseBLEClient+PeripheralDelegate.swift:152`
- **Status:** open  |  verifier confidence: high  |  fix risk: needs-device-testing

**Evidence.** The off-main fast path in didUpdateValueFor (lines 83-98) skips main-thread side effects for any notification value that contains no control frame: `guard shouldDispatchNotificationSideEffectsToMain(value, characteristic: characteristic) else { recordSkippedNotificationSideEffect(...); return }`. That predicate whitelists only `case V5PacketType.commandResponse, V5PacketType.puffinCommandResponse, V5PacketType.event, V5PacketType.metadata, V5PacketType.puffinMetadata: return true` — it omits `V5PacketType.historicalData` (47) and `historicalIMUDataStream` (52). The CBCentralManager is created on `coreBluetoothQueue` (GooseBLEClient+Commands.swift:10-16), so the delegate is always off-main and this fast path always applies. Consequently `handleHistoricalSyncValue` (GooseBLEClient+HistoricalHandlers.swift:7) is never invoked for data-only values, and the in-scope accounting `case V5PacketType.historicalData, V5PacketType.historicalIMUDataStream: historicalPacketsReceivedThisSync += 1 ... scheduleHistoricalIdleCompletion(reason: "historical_data_idle")` (HistoricalHandlers.swift:25-28) is dead for the bulk of the transfer (type-47 bursts are almost entirely data frames; only values that happen to also carry a metadata/response frame get through). Effects: (1) any chunk that streams >12s of pure data between metadata frames lets `historicalIdleWorkItem` fire mid-transfer; `retryHistoricalTransferAfterIdleIfNeeded` (DebugAndSync.swift:389-393) guards on `historicalPacketsReceivedThisSync == 0`, sees 0, and re-issues GET_DATA_RANGE into a live stream, and after `historicalTransferMaxRequestAttempts = 3` calls `failHistoricalSync("...produced no historical packet bodies...")` even though packets flowed the whole time; (2) after HistoryComplete the same count==0 path triggers spurious full re-pull cycles instead of `completeHistoricalSync`; (3) progress callbacks and the completion toast always report 0 packets ("No missed packets found" / "Historical metadata captured but no packet bodies received"); (4) it breaks the preserve-mode ACK suppression (see separate finding). historicalPacketsReceivedThisSync has exactly one increment site (HistoricalHandlers.swift:26) — there is no alternate counting path.

**Refined fix.** In shouldDispatchNotificationSideEffectsToMain (GooseSwift/GooseBLEClient+PeripheralDelegate.swift:152-161), add a case that dispatches historical packet types to main only while a V5 sync is active: `case V5PacketType.historicalData, V5PacketType.historicalIMUDataStream: if isHistoricalSyncing { return true }; continue`. This preserves the perf win for the GEN4 100 Hz realtime streams (isHistoricalSyncing is false on GEN4 by construction, since beginHistoricalSync requires supportsV5HistoricalSync) while restoring the counter increment and historical_data_idle re-arm at HistoricalHandlers.swift:25-28 during V5 syncs. Two refinements: (a) isHistoricalSyncing is mutated on the main thread and would now be read on coreBluetoothQueue — an unsynchronized Bool read; it is set before GET_DATA_RANGE is written and cleared only after terminal handling, so the window is benign, but if stricter correctness is wanted, mirror it into an atomic/locked flag (a pattern already used for gen4ProbeLock at Commands.swift:1229) set/cleared in beginHistoricalSync/completeHistoricalSync/failHistoricalSync. (b) If main-thread pressure during V5 bursts is a concern, instead keep the skip but hop a lightweight count to main: in the fast path, when isHistoricalSyncing and the value contains 47/52 frames, DispatchQueue.main.async a closure that does historicalPacketsReceivedThisSync += n, publishHistoricalPacketCountIfNeeded(), and scheduleHistoricalIdleCompletion(reason: "historical_data_idle") without carrying the payload. Leave gen4ObserveRawNotification untouched — it is the GEN4 backfill path and already runs before the skip guard. Needs validation against a live fd4b strap (the affected machine is unreachable on the GEN4 band).

### [LOW] Sync can be declared "synced" the moment the final HISTORICAL_DATA_RESULT write is queued; a subsequent write failure (e.g. dead link) is silently ignored because isHistoricalSyncing is already false

- **Where:** `GooseSwift/GooseBLEClient+HistoricalCommands.swift:133`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** In writeHistoricalCommand, the ACK is fire-and-forget: `pendingHistoricalCommand = nil; historicalCommandTimeoutWorkItem?.cancel()` (lines 100-101), then right after `activePeripheral.writeValue(...)` it runs `if historyCompleteReceived { completeHistoricalSync(reason: "history_result_ack_sent_after_complete") }` (lines 133-137), setting isHistoricalSyncing=false before CoreBluetooth confirms the write. The write-error path in didWriteValueFor only fails the sync `if isHistoricalSyncing && characteristic.uuid == commandCharacteristic?.uuid` (PeripheralDelegate.swift:307-309), so a failed final ACK write (including the documented zombie-link "The specified device is not connected." case) leaves the UI showing "Synced" while the band never received the trim ACK. Side effect: the unreachable `.historicalDataResult` response branch in handleHistoricalCommandResponse (HistoricalHandlers.swift:482-489) can never match because pendingHistoricalCommand was cleared, so a band-side FAILURE result for the ACK is also invisible. Consequence is bounded — the band re-sends the untrimmed chunk on the next sync (duplicates downstream) rather than losing data — but the success report is wrong and the duplicate re-pull is unexplained to the user.

**Refined fix.** In writeHistoricalCommand (GooseBLEClient+HistoricalCommands.swift:127-138), when kind == .historicalDataResult and historyCompleteReceived, do not call completeHistoricalSync synchronously. If the write was issued .withResponse, set a flag (e.g. awaitingHistoryResultAckWriteConfirmation, storing the run ID) and keep isHistoricalSyncing=true; in peripheral(_:didWriteValueFor:error:) (PeripheralDelegate.swift:319-321 success branch), when the flag is set and characteristic == commandCharacteristic, clear it and call completeHistoricalSync(reason: "history_result_ack_write_confirmed") — the existing error branch at lines 307-309 then fails the sync naturally (and recoverFromDeadLink still fires). Add a short fallback (e.g. 5s DispatchWorkItem keyed on historicalSyncRunID) that completes the sync anyway if no callback arrives, and complete immediately as today when writeType == .withoutResponse (didWriteValueFor never fires for those), so the sync can never hang in "syncing". Optionally, in the failure case also leave a record that the trim ACK was not delivered so the next sync's duplicate chunk re-pull is explained.

### [LOW] Off-by-one in HISTORICAL_DATA_RESULT ACK payload builder: rejects a minimal-length HistoryEnd metadata payload that it could fully parse

- **Where:** `GooseSwift/GooseBLEClient+Parsing.swift:834`
- **Status:** open  |  verifier confidence: high  |  fix risk: safe

**Evidence.** `guard payload.count > 21 else { return nil }` followed by `result.append(contentsOf: payload[13..<21])` (Parsing.swift:833-841). The slice only requires payload.count >= 21, but the guard demands >= 22, so a HistoryEnd metadata payload of exactly 21 bytes (the minimal 12-byte body whose bytes 4...11 are the trim value the comment says it mirrors) is rejected. The in-scope caller (HistoricalHandlers.swift:550-559) then logs "result_ack.unprepared" and never queues an ACK, stalling the chunk handshake until the 12 s idle/retry machinery kicks in. Mitigation: device payloads appear to be padded to 4-byte multiples (cf. buildV5CommandFrame padding), which would make an exactly-21-byte payload unlikely — hence low severity — but the guard contradicts the code one line below it.

**Refined fix.** In /Users/schoebela/PycharmProjects/goose/GooseSwift/GooseBLEClient+Parsing.swift line 834, change `guard payload.count > 21 else { return nil }` to `guard payload.count >= 21 else { return nil }`. This is safe: it strictly widens accepted inputs to exactly the set the slice `payload[13..<21]` can handle (indices 13...20), with no other reads past index 20 in the function. Optionally add a unit test feeding a 21-byte synthetic HistoryEnd metadata payload to historicalDataResultPayload(fromHistoryEndMetadataPayload:) asserting it returns [1] + bytes 13..<21, since the ACK builder currently has no test coverage.

## swift-appmodel

This scope is the iOS app's central coordination layer: GooseAppModel (a @MainActor ObservableObject) plus extensions that route raw BLE notifications through reassembly/parse/import queues, run timed health-packet capture sessions, drive the Overnight Guard state machine (JSONL spool + SQLite mirror + manifest/status sidecars + final historical sync + export), record activities, and coalesce UI state via aggregators. Overall the code is unusually defensive — bounded write queues, throttled publishing, queue-confined reassembly buffers, lock-protected depth counters — and contains no third-party endpoints (privacy constraint holds). The real weaknesses are at the edges: the overnight final-sync state machine can wedge with no retry or timeout, per-packet synchronous status-file rewrites on the main thread during sync bursts, MainActor state read unsynchronized from the CoreBluetooth queue (masked by Swift 5.0 language mode), synchronous spool I/O on the CoreBluetooth queue during guard sessions, an error path that leaves a capture session permanently open, and a background-task expiration handler that ends its task asynchronously.

### [MEDIUM] Overnight final sync wedges permanently if historical sync is blocked after the live-stream pause (no retry, no timeout, polls disabled, background task leaked)

- **Where:** `GooseSwift/GooseAppModel+OvernightRun.swift:140`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** In requestOvernightGuardFinalSync, after setting overnightGuardFinalSyncPending = true, cancelling range polls, beginning a critical background task, and stopping the live physiology streams, the 2.2 s continuation bails out without any cleanup: `guard self.ble.canSyncHistorical else { self.overnightGuardStatus = "Final sync blocked after live-stream pause: \(self.ble.historicalSyncStatus)" ... return }`. overnightGuardFinalSyncPending stays true forever: re-tapping final sync hits `guard !overnightGuardFinalSyncPending else { overnightGuardStatus = "Final sync already running"; return }` (line 109), scheduleOvernightGuardRangePoll refuses to run (`guard overnightGuardActive, !overnightGuardFinalSyncPending`, line 378), live capture has already been stopped, and the critical background task begun at line 122 is never ended (it leaks until iOS force-expires it). The same wedge occurs if the sync starts but never reaches a terminal GooseHistoricalSyncProgress (e.g. the documented silent-disconnect dead-link) — there is no watchdog/timeout covering the finalSyncPending state. The only escape is manually stopping the guard, abandoning the final sync's backfill data.

**Refined fix.** In the blocked branch of the 2.2s closure in requestOvernightGuardFinalSync (/Users/schoebela/PycharmProjects/goose/GooseSwift/GooseAppModel+OvernightRun.swift, lines 140-144), before the `return`: (1) set `self.overnightGuardFinalSyncPending = false`; (2) call `self.endOvernightGuardCriticalBackgroundTask(reason: "final_sync_blocked_after_live_stream_pause")`; (3) call `self.resumeOvernightGuardStreamsIfReady(reason: "final_sync_blocked_after_live_stream_pause")` - with the pending flag now cleared this restarts physiology capture immediately if the link is ready and re-arms range polling via its existing `!overnightGuardFinalSyncPending` gate (it also degrades gracefully to "resume_waiting_for_ready" + the existing ble_ready hook in Lifecycle.swift:88 if the band is still disconnected); (4) optionally schedule one automatic retry of requestOvernightGuardFinalSync after Self.overnightGuardRangeBlockedRetryInterval so an overnight unattended run still gets its final sync once the band reconnects. A separate stall watchdog for an already-started sync is NOT needed: GooseBLEClient already emits terminal failed progress on command timeout, disconnect, Bluetooth-off, and write failure, which the existing handleOvernightHistoricalSyncProgress finalSyncPending branch converts into drain + completeOvernightGuard. Secondary hardening (same family): completeOvernightGuard should also call endOvernightGuardCriticalBackgroundTask for non-"final_sync" reasons (e.g. manual_stop), since today only the export completion paths end the task.

### [MEDIUM] writeOvernightGuardStatus runs per data packet: synchronous full status-file rewrite + SQLite enqueue + battery poll on the main thread during sync bursts

Overall health is decent — the state machine guards transitions correctly, GPS accuracy gating and CRC-free UI code are clean, and no privacy violations or non-user endpoints exist in scope — but it has one systemic gap (zero persistence of in-flight workouts, so a crash/jetsam loses the session and orphans the Rust capture session), a classic pause/resume GPS teleport bug that inflates distance/pace/elevation, an ineffective Live Activity throttle that updates roughly every second instead of every 15 s, and several placeholder metrics (time-based calories, '+12 s' elapsed, '+2 kcal' total) shipped as if they were real measurements. Note: ActivityLocationTracker.startIfAuthorized has no callers (dead code), so nothing restarts GPS after a relaunch even if a workout-restore path were added.

### [HIGH] In-flight workout is held entirely in memory; app kill/crash mid-workout loses the whole session

(3) At launch, next to cleanupOrphanedActivityCaptureSessions (GooseAppModel.swift:417), if a snapshot exists, finalize it through the existing finishActivityRecording path with endedAt = max(snapshot.lastUpdatedAt, persistence.lastImportedFrameAt) and syncStatus "recovered" (or prompt the user to resume/discard), which also closes the orphaned capture session with the true end time instead of letting the zero-frame janitor stamp it with relaunch time. Run the recovery before cleanupOrphanedActivityCaptureSessions so the janitor doesn't close the session first.

### [MEDIUM] Elevation gain sums every positive GPS altitude jitter (accepting up to 50 m vertical accuracy), inflating the metric

- **Where:** `GooseSwift/ActivityLocationTracker.swift:151`
- **Status:** open  |  verifier confidence: high  |  fix risk: needs-device-testing

**Evidence.** 'if lastAcceptedLocation.verticalAccuracy >= 0, location.verticalAccuracy >= 0, lastAcceptedLocation.verticalAccuracy <= 50, location.verticalAccuracy <= 50 { elevationGainMeters += max(0, location.altitude - lastAcceptedLocation.altitude) }'. **Refined fix.** In ActivityLocationTracker: (1) tighten the elevation gate from <= 50 to <= 15 m verticalAccuracy; (2) replace the raw rectified sum with a deadband baseline: add `private var elevationBaselineAltitude: CLLocationDistance?`; in append(_:), when both fixes pass the gate, set the baseline on first use, compute `threshold = max(3.0, location.verticalAccuracy)`, then if `location.altitude - baseline >= threshold` do `elevationGainMeters += location.altitude - baseline; elevationBaselineAltitude = location.altitude`, else if `baseline - location.altitude >= threshold` just rebase `elevationBaselineAltitude = location.altitude` (descents rebase without subtracting). Validate thresholds with an on-device flat-route run before shipping (matches fix_risk: needs-device-testing).

## swift-coach

The Coach subsystem is the app's LLM coaching layer: a SwiftUI overview + chat UI (CoachView/CoachChatScreen/CoachComposer/CoachMessageViews), a ChatGPT device-code OAuth client with Keychain token storage (CodexEmbeddedAuth.swift), local "tool context" builders that serialize the user's health state into JSON for the model (CoachLocalToolContext.swift, plus an unused near-duplicate in CodexCoachSupport.swift), canned prompt builders that inline biometric values (CoachTips.swift), a UserDefaults-backed conversation store (CoachChatTypes.swift), and a small bounded BLE message buffer (GooseMessageStore.swift, clean — main-thread confined, capped at 300). Overall health is decent: OAuth tokens are properly in Keychain (not UserDefaults), transcripts and message buffers are bounded, and requests set "store": false. The real issues are on the privacy surface — a broad, force-triggered biometric payload leaves for OpenAI's chatgpt.com backend on every coach turn while the sign-in copy promises a per-use "approval" that does not exist, and the chat transcript (with biometric tool results) is persisted in plaintext UserDefaults — plus an actor-reentrancy race on token refresh and a fragile device-login poll loop.

### [MEDIUM] Actor-reentrancy race in token refresh can use a stale rotated refresh token and spuriously kill the session

- **Where:** `GooseSwift/CodexEmbeddedAuth.swift:214`
- **Status:** open  |  verifier confidence: high  |  fix risk: moderate

**Evidence.** `func storedAuth(refreshIfNeeded: Bool = true) async throws -> CodexStoredChatGPTAuth? { guard var auth = try CodexSelfContainedAuthKeychain.load() else { return nil } ... auth = try await refreshStoredAuth(auth); try CodexSelfContainedAuthKeychain.save(auth); return auth }` — CodexSelfContainedAuthClient is an actor, but actors are reentrant across `await`: two overlapping calls (CoachView.onAppear fires `chat.refreshAuth()` -> `authClient.storedAuth(refreshIfNeeded: true)` while a send concurrently calls `storedAuth` in streamResponseLoop, OpenAICoachChat.swift:196) both load the same Keychain auth, both pass `auth.needsRefresh`, and both POST grant_type=refresh_token with the SAME refresh token. The code itself anticipates rotation (`refreshToken: tokenResponse.refreshToken ?? auth.refreshToken`, line 291), and with single-use/rotation-detected refresh tokens the losing call gets invalid_grant -> throws -> refreshAuth()'s catch sets `self?.auth = nil; self?.isSignedIn = false` (OpenAICoachChat.swift:51-54), signing the user out even though a valid token was just saved; the racing saves can also persist the older token pair last.

**Refined fix.** In actor CodexSelfContainedAuthClient (GooseSwift/CodexEmbeddedAuth.swift), deduplicate in-flight refreshes and re-check state after suspension: add `private var refreshInFlight: Task<CodexStoredChatGPTAuth, Error>?`. In storedAuth, after the needsRefresh check: if refreshInFlight is non-nil, `return try await refreshInFlight!.value` instead of issuing a second refresh. Otherwise create the task: inside it, re-load CodexSelfContainedAuthKeychain.load() and return early if the reloaded auth no longer needsRefresh (another caller already refreshed), else `let refreshed = try await refreshStoredAuth(current); try CodexSelfContainedAuthKeychain.save(refreshed); return refreshed`. Store it in refreshInFlight, `defer { refreshInFlight = nil }`, and `return try await task.value`. Secondary hardening in OpenAICoachChat.swift refreshAuth()'s catch (lines 50-56): before nil-ing auth/isSignedIn on a refresh error, attempt `authClient.storedAuth(refreshIfNeeded: false)` and keep the session if a stored token still exists, so a transient refresh failure does not spuriously sign the user out.

## swift-views

Audited the SwiftUI view layer (Health*/Home* dashboard, chart, and drill-down views) of the GooseSwift iOS app. Crash-safety is genuinely good: every chart primitive guards empty series (`isEmpty` branches), divisions are clamped with `max(...,1)`, indices are clamped or derived from guarded ranges (e.g. `0..<max(count-1,0)`), and no force-unwraps on dynamic data exist in scope — I found zero index-out-of-range or divide-by-zero crash paths. The real problems are: (1) a static API token to the health-data VPS hardcoded in source and committed to git, on a publicly-routable endpoint; (2) a systemic performance anti-pattern where computed properties wrapping full-store scans (filter+sort of up to 100k in-memory HR samples under a lock, on the MainActor) are re-evaluated many times per body render, and bodies re-render at least every ~5 s while the band streams (packetImportRevision publishes on a 5 s throttle, capture UI updates at 1 s); (3) the Today screen's 30 s auto-refresh timers are stored as view-struct properties, so those same frequent parent re-renders recreate/resubscribe the publisher and the timer never fires while the band is connected; and (4) the VPS feed classes swallow all network/decode errors. No third-party/non-user endpoints were found — all network calls go to the user's own VPS.
